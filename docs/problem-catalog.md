# Problem Catalog

This is the companion reference for [`docs/parallel-runner-guide.md`](./parallel-runner-guide.md)
§2, where you set `PROBLEM_ID` in a cluster overlay's `patch.yaml`. Each row below maps
one runnable `PROBLEM_ID` (the exact key in `sregym/conductor/problems/registry.py`'s
`PROBLEM_REGISTRY` dict) to the benchmark app it targets, what kind of failure it is,
whether the fault is injected inside the app itself or at the surrounding
Kubernetes/infrastructure layer, how it's actually implemented, and a one-line
description of what breaks.

This reflects the **current `registry.py`** as of this writing: **117 active problem
IDs** — more than the 90 problems reported in the original SREGym problem set. The
extra ~27 were added in later commits: an admission-webhook/PSA family
(`admission_webhook_outage_hotel_reservation`, `admission_webhook_tls_mismatch_hotel_reservation`,
`mutating_webhook_resource_limits_social_network`, `psa_restricted_blocks_recreation_hotel_reservation`,
`cumulative_admission_webhook_timeout_hotel_reservation`), a K8s Operator Misoperation
family (`operator_*`, targeting a TiDB-operator-managed cluster), a Calico/networking
family, and several one-off node- and workload-level faults
(`node_clock_drift_hotel_reservation`, `kubelet_eviction_threshold_misconfig`,
`cronjob_sidecar_blocks_completion_hotel_reservation`, `hpa_missing_effective_cpu_request_hotel_reservation`,
`priority_preemption_cascade_hotel_reservation`, `dev_shm_exhaustion_hotel_reservation`,
`node_conntrack_exhaustion_hotel_reservation`, `pod_cidr_exhaustion_hotel_reservation`, etc.).

The table is grouped by **Fault type** (mirroring the pre-existing `Problem List.md`
taxonomy), since that's usually how you'd pick a scenario for an experiment — e.g.
"give me a Network Failure" or "give me a Security Failure." Within each group, rows
are unordered. Columns:

- **Target app / scope** — which benchmark app namespace the fault lands in:
  `astronomy_shop`, `hotel_reservation`, `social_network`, `train_ticket`, or
  `cluster-wide` for faults that aren't scoped to one of the four standard apps.
- **Injection target** — `App` if the fault modifies something inside the benchmark
  app's own namespace/workload (image, env var, service selector, app-level
  auth/config, in-app HTTP fault flags); `Infrastructure` if it modifies a
  Kubernetes control-plane resource, node/kubelet/OS setting, CNI/DNS, PriorityClass,
  PSA policy, admission webhook, storage class, or emulates a hardware fault. A few
  rows are genuinely mixed and are annotated accordingly.
- **Injector mechanism** — the actual mechanism the `inject_fault()` method uses.
- **Origin** — `New` (bespoke to this repo) or `AIOpsLab` (adapted from the AIOpsLab
  benchmark), from `Problem List.md` where available.

Only the **117 active** IDs are usable as a `PROBLEM_ID` value today. A further 15
problem classes exist in source and are imported by `registry.py` but are commented
out of `PROBLEM_REGISTRY` — see the [appendix](#not-yet-wired-into-the-registry) at
the bottom.
